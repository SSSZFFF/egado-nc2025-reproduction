## 设置

- `--strategy passwise --pass-top-n 36,36`
- 每个 Pass 开头按当前 `|linear_prior|` 排序 Top-N；Pass 内每格最多评估一次，不重复、不做中途刷新
- Pass 1 用初始伴随；Pass 2 前若 Pass 1 有 accepted flip，则刷新一次伴随（4 solves）
- `--max-fdtd 80`，`--enable-refresh`

## 结论

v5 的“每格至多一次 + Pass 间刷新”确实解决了 v4c 的重复重测问题，Pass 1 也成功吃到了 `(15,12)`、`(16,15)`、`(19,25)`、`(23,22)`，但：

1. **`(23,21)` 在两个 Pass 中都没有变成正增益**：Pass 1 −0.005726，Pass 2 −0.002749；
2. 这说明 `(23,21)` 的激活不是“只翻完 `(15,12)`、`(16,15)`、`(20,13)` 就会自动发生”，而是依赖更长的中间状态路径（baseline 到 226 solves 才触发）；
3. Pass 2 只刷新了一次，且没有足够多的前置翻转，`(23,21)` 始终被一阶 prior 判为负；Pass 2 反而把 `(15,12)`/`(16,15)` 翻回成负值；
4. v5 最终 0.866310，优于 v4c 0.859395，但仍低于 v3b/v3c，距离 baseline 0.886449 还差 0.020139。

因此“Passwise Top-36”是一个干净、可复现的实验，但它还不是解决 `(23,21)` 延迟激活的充分方案；核心问题是 **状态路径不够长/不对，不是候选池不够大**。

## 下一步建议

- 不要直接上 4 模；先用 baseline 的中间态路径作为“状态课程”，验证 `(23,21)` 在哪个具体前驱翻转集合下变正。
- 可以把 Pass 1 的 `(15,12)`、`(16,15)`、`(19,25)`、`(23,22)` 作为固定前缀，再在接近 `sweep2 step76` 的状态做局部 Pass 2；这样 `(23,21)` 才可能被正确重测。
- 若继续纯搜索，应允许 Pass 3/4 并在每 Pass 后保留更多前缀翻转，而不是只跑两个 Pass。
